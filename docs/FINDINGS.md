# Findings

**2026-11-12.** `mca-check`, a from-scratch C++20 implementation of the 2018 MCA ARMv8 axiomatic
model, reproduces the paper's published results on every test where both the test's source and its
result can be identified: **45 of 45 tests, as whole sets of allowed final states** (compared on the
variables each test's condition names), not as yes/no verdicts. On a Galaxy S25 Ultra (Qualcomm
Oryon cores), **147 million test runs produced no state the model forbids**, while every
distinction the model draws showed up in the silicon. Each pair differs by one clause of the model:
`PPOCA` seen and `PPOAA` never; `ctrl` seen and `ctrl`+`ISB` never; `LDAPR` seen and `LDAR`
never; `IRIW` seen and `IRIW+addrs` never.

## 1. The checker against published answers

Details are in [results/oracle.md](../results/oracle.md), regenerated by `python3 tools/oracle.py`.

| Reference | Tests | Agreement |
| --- | ---: | --- |
| The paper's ARMv8-axiomatic model logs: 7 of the paper's own tests, 21 from herd's catalogue, 17 written here to the exact conditions in the logs | 45 | **45 match**, state set for state set |
| herdtools7 `kinds.txt` (today's model, verdict only) | 42 | 33 match; 9 differ (below) |
| Same name as a paper log but a different condition | 6 | not compared; both conditions are listed |
| Not supported: a condition without parentheses (2), a post-indexed store (1), an init value `5;` (1), a file that is a symlink (1) | 5 | — |

**What the paper's logs check, and what they don't.** The 45 tests use plain loads and stores,
address/data/control dependencies, `ISB`, the three `DMB`s, `LDAR` and `STLR`. So the `internal`
and `external` axioms, and every `dob` clause and every `bob` clause except `[A | Q]` with `Q`, are
checked against the paper. **Load/store-exclusive, the Armv8.1 atomics (`SWP`, `CAS`, `LDADD`), the
`atomic` axiom and `LDAPR` are checked only against today's `kinds.txt`.** The paper's own atomics
suite (`ATOM`) uses a store-exclusive bookkeeping convention that could not be rebuilt from its logs
with confidence.

**How the references were kept independent.** No expected answer was typed by hand. The tests come
from the paper's site and herdtools7; the answers come from the paper's own model logs. A log is
used only when its condition equals the test's: four of herd's catalogue tests (`CoRR`, `CoRW1`,
`CoRW2`, `CoWR`) share a name with a paper test but are different tests, and the script says so
instead of failing or quietly passing them.

**Every axiom is exercised.** Turning each one off changes the allowed states: internal for 21
tests, external for 58, atomic for 5 (`MP+rel+SWP*`, `R+CAS+DMBLD`).

**The nine differences from today's herd model.**
- `CSEL` (2 tests). *Explained:* today's `aarch64deps.cat` gives "pick" instructions their own
  dependency relations (`pick-ctrl-dep` and others). The catalogue keeps these tests in an
  `aarch64-pick` set. Here, `CSEL` passes on a data dependency through the flags, as in the 2018
  definition.
- Atomics whose result register is `XZR` (5 tests, all named `…noret…`). *Hypothesis:* today's model
  gives an atomic with no return register weaker ordering than one that returns a value, and the
  2018 model makes no such distinction. This is read off the test names and verdicts, not from a
  definition.
- `CAS` register dependencies (2 tests). *Hypothesis:* today's model treats the compared register
  `Rs` specially, both as a source of the write and as the result of a successful `CAS`. One rule
  was tried: the write depends on `Rs`. It fixed `LB+rel+CAS` and broke `CAS+data2` and
  `MP+rel+CAS-addr`, so it was reverted. The note is in `model.cpp`.

## 2. The runner, before any phone

- 38 tests generated from the same parser the checker uses (`mca-check --describe`).
- **Disassembly check:** in the static arm64 binary (NDK r30, Android API 29), all 80 thread bodies
  contain exactly their test's instructions, in order (`hw/verify_disasm.py`). The first check
  flagged 5 bodies. The cause was the check itself, not the code: labels inside the asm became
  symbols. Assembler-local labels (`.L…`) fixed it.
- **Host smoke test** (`hw/host_smoke.c`, x86 under WSL, 200,000 runs per test). The harness gives
  x86's known answers:
  - `SB`'s relaxed state seen 70 and 78 times (pinned / unpinned): the threads overlap;
  - `SB` with `mfence`: 0;
  - `MP`: 0.

  The forbidden-state counter, the JSON and `compare.py` all worked. A configuration with fewer CPUs
  than threads is skipped, not run.
- LSE atomics and `LDAPR` tests are skipped on a core that lacks them (`AT_HWCAP`), instead of
  crashing on an illegal instruction.
- Each thread records which CPUs it ran on, so a pinning failure shows in the results.

## 3. On the silicon: Galaxy S25 Ultra, 2026-11-12

**The phone.** SM-S938B, Snapdragon 8 Elite (SM8750), Android 17, kernel 6.6. `/proc/cpuinfo`
reports implementer `0x51` (Qualcomm), part `0x001` on all eight CPUs: Qualcomm's own Oryon cores,
an implementation of the Arm architecture by an architecture licensee, not an Arm-designed core.
Six run up to 3,532 MHz (cpu0–5), two up to 4,473 MHz (cpu6–7). LSE atomics and `LDAPR` are both
present. Thermal status was 0 before and after every run.

**The run.** 38 tests × 1,000,000 instances × 4 configurations (unpinned; cpu0–3; cpu6–7; cpu6,0,7,1
across clusters). 3- and 4-thread tests are skipped in the 2-CPU cluster, not doubled up. Every
pinned thread stayed on its CPU. The full table is [results/hardware.md](../results/hardware.md).

**First, the harness had to be fixed.** The first full run synchronised threads with a spin barrier
before each instance. It produced no forbidden state, but almost no allowed relaxations either: `SB`
44 times in 4 million, `IRIW` never. That made every zero meaningless, because the threads were
barely overlapping. A barrier's release travels from core to core (tens of nanoseconds or more),
while a test body takes a few nanoseconds. Synchronising instead on the Arm generic timer
(`CNTVCT_EL0`, one count every core sees) lines the threads up on the same tick:

| Test | Spin barrier (4 configs) | Time base (4 configs) |
| --- | ---: | ---: |
| `SB` | 44 | **399,821** |
| `IRIW` | 0 | **4,918** |

Both runs are kept and both are in the table. At most 2.1% of instances started late (a thread
reached the tick after it had passed), so the time base held.

**Results (time base).**

- **No forbidden state, in 147 million instances**: not in the coherence controls (`CoRR`, `CoRW1`,
  `CoRW2`, `CoWR`, `CoWW`), not with barriers or release/acquire, not with dependencies, and not in
  the multicopy-atomicity tests (`IRIW+addrs`, `WRC+addrs`, `WRC+data+addr`,
  `ISA2+dmb.sy+data+addr`). That last group is the paper's central claim, held on the cores of a 2025 phone, from
  a vendor other than Arm. These are 0 in 3 million instances each, against 4,918 sightings of the
  unordered `IRIW`.
- **Each pair the model separates, the silicon separates too:**

  | Allowed, and seen (max per million) | Forbidden, and never seen | The clause that differs |
  | --- | --- | --- |
  | `PPOCA` 461 | `PPOAA` 0 | `(addr\|data);rfi` with no `ctrl;rfi`: a speculative store is forwarded to a later load on the same thread |
  | `MP+dmb.sy+ctrl` 6,456 | `MP+dmb.sy+ctrlisb` 0 | `(ctrl \| addr;po);[ISB];po;[R]` |
  | `SB+dmb.sy+rel-acqpc` 35,877 | `SB+dmb.sy+rel-acq` 0 | `[L];po;[A]` covers `LDAR` (A) but not `LDAPR` (Q) |
  | `IRIW` 4,888 | `IRIW+addrs` 0 | `addr` in `dob`, plus MCA |
  | `MP` 17,830 | `MP+dmb.sy+addr`, `MP+dmb.st+addr` 0 | `bob`'s `dmb.st` clause and `addr` |

- **Allowed, never observed:** `LB`, `2+2W`, `S`, `MP+po+addr`. Every one of these needs either a
  write to overtake an earlier write, or a write to overtake an earlier read. Every relaxation that
  *was* seen needs only a read to overtake: a later read passing an earlier write (`SB`, `R`), or a
  later read passing an earlier read (`MP`, `IRIW`, `PPOCA`). With `SB` seen 400,000 times, that is
  a consistent pattern rather than missed overlap. *Hypothesis:* these Oryon cores make stores
  visible in program order and never let a store overtake a load. That is stronger than the
  architecture requires, so software must not rely on it: the next Arm core may differ.
- **Placement matters for rates, not for correctness.** Relaxations are rarest across clusters
  (`MP` 5 per million, against 17,830 on the two fast cores), where communication is slowest.
